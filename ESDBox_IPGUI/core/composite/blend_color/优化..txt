这份 ipgui_blend_color() 里，最值得优化的 3 个点，我按“收益 / 改动比”给你排：

1. 把每像素的 combine_opacity_and_premultiply 改成“每次绘制预计算 LUT”

这是收益最大的一点。

你现在每个有效像素都在做这件事：

mask_opacity_combined =
    (u8_t)(((u32_t)opacity * mask_val + 127) >> 8);

premult = ipgui_color_combine_opacity_and_premultiply(
    &color, mask_opacity_combined);

这意味着每个像素都重复做：

一次 opacity * mask

一次 alpha 组合

三次 r/g/b * alpha

而同一次 ipgui_blend_color() 调用里：

color 是固定的

opacity 是固定的

真正变化的只有 mask_val

所以最适合改成：

做法

在进入双层循环前，预计算一个 256 项 LUT：

lut[mask] = 对应 mask 值下的 premultiplied color

或者至少：

alpha_lut[mask]

premult_lut[mask]

这样像素循环里就只剩：

premult = premult_lut[mask_val];
if (IPGUI_COLOR_A(premult) > 2) {
    blend_fn(premult, &dest_cr_buf[row_pix_off], blend_mode);
}
收益为什么大

因为这一步现在是每个像素都会反复算，而且乘法不少。
边缘 AA 场景里，mask 值虽然很多，但本质就 256 种。

内存代价

如果 ipgui_color_t 是 4 字节，那就是：

256 * 4 = 1024 bytes

只要 1KB 左右，通常很值。

推荐程度

强烈推荐，优先级 1。

2. 给 mask == 0 / mask == 255 做真正的快路径，最好按“连续段”处理

这是第二个最值的优化点。

你现在的代码是逐像素判断：

mask_val = mask_row[x];

if (mask_val > 2) {
    ...
}

但你前面的圆角/ring mask 有一个很重要的特征：

一大段是 0

一小段是 渐变边缘

另一大段常常是 255

也就是说，真实分布不是“随机 mask”，而是很适合做 span 优化。

当前问题

即使 mask_val == 255，你也还是走：

opacity 组合

premultiply

blend

这其实很亏。

因为：

mask == 0：直接跳过

mask == 255：完全可以走预先准备好的固定 premult color

如果 mask == 255 且最终 alpha 接近全不透明，还能进一步退化成更快的 solid/opaque 路径

做法

至少做两层优化：

第一层：像素级快路径
if (mask_val <= 2) {
    // skip
} else if (mask_val >= 253) {
    // 直接用 full-mask 对应的 premult color
    blend_fn(full_premult, ...)
} else {
    // 渐变区走 lut
}
第二层：连续段快路径

如果一行里有连续的 255 段，可以直接：

找 run

连续调用专用 inner loop

甚至在高 alpha 时退化成 fill

这个在圆角/圆环里收益会很明显，因为 mask 本来就是 span 型结构。

收益为什么高

因为圆角/ring 的 mask 天然就不是“全随机 alpha 图”。
你的几何模块已经帮你制造了很强的可压缩性，只是 ipgui_blend_color() 还没吃到这个红利。

推荐程度

强烈推荐，优先级 2。

3. 去掉像素内层里的函数指针调用，改成按像素格式分派专用循环

这是第三个最值得改的点。

你现在虽然把 blend_fn 提前取出来了：

premult_blend_func_t blend_fn = premult_blend_table[surf->pix_fmt];

但真正混合时仍然是：

blend_fn(premult, &dest_cr_buf[row_pix_off], blend_mode);

也就是每个像素一次函数指针调用。

在桌面 CPU 上这不算太夸张，
但在嵌入式上，尤其是 tight loop 里，这种间接调用会带来：

调用开销

不利于编译器内联

不利于寄存器优化

不利于流水线预测

做法

把 ipgui_blend_color() 按 pix_fmt 分支到专用 inner loop：

例如：

switch (surf->pix_fmt) {
case PIX_FMT_RGB565:
    // 专用 rgb565 loop
    break;
case PIX_FMT_RGB888:
    // 专用 rgb888 loop
    break;
...
}

这样内层直接写死调用：

ipgui_builtin_premultiplied_color_blend_to_rgb565(...)

或者干脆把关键混合逻辑做成 static inline。

为什么它排第 3

因为这项优化是实打实有效的，但通常不如前两项收益大。
前两项是在减少运算量，这一项更像是在压缩调度开销。

推荐程度

推荐，优先级 3。

我给你的排序结论
第一名

预计算 mask -> premult color LUT

这是最值的。

第二名

利用 mask 的 0 / 255 / 渐变段特征做快路径，最好按连续段处理

这和你的圆角/ring 模块特别匹配。

第三名

去掉像素内层的函数指针调用，改成 pix_fmt 专用循环

这个也值得做，尤其在 MCU 上。

如果只允许先改一个

先改这个：

把 ipgui_color_combine_opacity_and_premultiply() 从像素循环里挪出去，改成 256 项 LUT。

这是改动相对小、收益最大的点。

一个很短的实战建议

如果你下一步要优化，我建议顺序就是：

premult_lut[256]

mask==0 / 255 快路径

RGB565 专用内层循环

这三个做完，你这套圆角 + blend 在嵌入式上的观感会明显更好。
