# IPGUI 工程化改造路线

## 一、自我批评

### 1.1 只有引擎，没有产品

写了一年半，代码量不小，但从用户视角看只有一个东西：**渲染效果好看，但什么都做不了。**

一个 GUI 框架最基本的闭环是"建窗口 → 放按钮 → 点按钮有反应 → 屏幕上看到变化"。这个闭环在 IPGUI 里是断的——按钮的头文件定义了，实现是空的；事件系统只定义了 PRESSED/RELEASED/HOVER，长按双击全没有；输入系统的 convert_event_cb 里 KEY_DOWN 分支直接返回了 `IPGUI_ERR_NOK`。用户拿到代码，不知道该从哪里开始写第一行界面。

### 1.2 没有构建系统

几十个 `.c` 文件散落在十几层目录里，没有 Makefile，没有 CMakeLists。文件之间的依赖关系只存在于我的脑子里——用户想用 box_shadow，他不知道要同时包含 `ipgui_edge_wdf_mask.c`、`ipgui_color.c`、`ipgui_memory.c`、`ipgui_math.c` 和另外五六个基础文件。

这不是"缺少文档"的问题，是用户根本没法编译。一个没法编译的库，代码质量再高也没用。

另外，[ipgui_conf.h](core/../ipgui_conf.h) 里写死了 6MB 内存、2560x1440 分辨率。没有最小配置档，没有按模块裁剪的开关。用户不知道关掉 SDF 阴影、关掉渐变之后这个东西能不能在 64KB RAM 的 MCU 上跑——实际上我也没有测试过。

### 1.3 控件库是空壳

`ipgui_button.h`、`ipgui_switch.h`、`ipgui_slider.h`、`ipgui_label.h` 这几个头文件定义了结构体和 API 签名，但 `.c` 实现文件是空的或者只搭了骨架。SGL 有 30+ 个完整可用的控件，IPGUI 一个能点能看的按钮都没有。

### 1.4 输入系统只做了一半

输入系统的架构设计是完整的——多源注册、bitmap ID 分配、环形事件队列、pointer 事件状态机——这是用心的设计。但 `converter_state_t` 里 `key_press_start_time` 和 `key_long_press_triggered` 字段留了一年半，对应的语义转换逻辑一行没写。用户拿到的事件永远是瞬时 KEY_DOWN/KEY_UP，想判断长按得自己在每个控件里掐表。

### 1.5 过度设计了用不到的东西

矢量渲染管线搭了完整架子（path/stroker/curve/transform 四个模块），但实际被调用的只有 arc 渲染需要的切线计算。图片解码器支持 BMP/PNG/GIF/JPEG/QOI 五种格式，但没有 Image 控件来承载它们。基础设施层有 AVL 树、图、LRU 缓存、时间轮定时器，有一些在框架里根本没用到。

投入产出不成比例。花在"未来可能需要"上的时间，挤占了"现在就需要"的控件和构建系统。

### 1.6 没有许可证

整个仓库没有一个 LICENSE 文件。用户不知道该以什么条款使用、修改、分发这些代码。没有 OSI 许可证的开源项目在法律意义上不能用于商业产品。这是最低成本的修复，也是一直被忽略的最基本要求。

### 1.7 编码细节问题

- 大量注释是中文，对非中文开发者不友好
- 文件名前缀不统一（`ipgui_` 个别地方用了其他前缀）
- 头文件保护宏风格不一致（有的用 `#ifndef __XXX_H__`，有的用 `#ifndef XXX_H`）
- 存在在头文件里定义非 static 变量的问题（会导致多编译单元链接冲突）
- 存在未使用的函数和宏

## 二、改造路线

### 第一阶段：能编译（优先级最高）

**目标：** 用户 clone 下来，一行命令能编译出结果。

| 任务 | 说明 |
|---|---|
| 添加 `LICENSE` | MIT 或 Apache 2.0 |
| 编写顶层 `Makefile` | `make` 编译静态库 `libipgui.a`，`make demo` 编译 SDL2 模拟程序 |
| 确保 `port/sdl` 可编译 | 补全 SDL2 模拟的入口 `main.c`（初始化 → 建 page → 跑事件循环） |
| 提供最简配置档 | 在 `ipgui_conf.h` 按模块加 `#define IPGUI_USE_BOX_SHADOW 1` 之类的宏开关 |
| 写 `BUILDING.md` | 编译说明：依赖（SDL2）、编译步骤、如何裁剪模块 |

**验收标准：** `git clone → make demo → ./demo` 能看到一个带有框架界面的窗口。

### 第二阶段：核心控件 MVP（6 个）

**目标：** 能写一个完整的 demo 页面。

| 控件 | 说明 |
|---|---|
| Label | 文本显示 |
| Button | 带文本/颜色的可点击按钮 |
| Image | 调用已有 BMP/PNG 解码器 |
| Slider/Bar | 滑块和进度条复用相同渲染 |
| Checkbox/Switch | 开关选择 |
| Arc/Gauge | 调用已有 arc 渲染，差异化卖点 |

每个控件需要：
- `create()` 分配 + 初始化 widget
- `render_cb()` 调用框架的绘制 API
- `event_handler()` 处理 PRESSED/RELEASED/CLICKED 等事件
- `destroy()` 释放资源

### 第三阶段：输入语义补完

**目标：** 控件层能收到语义事件而非瞬时事件。

| 任务 | 说明 |
|---|---|
| 实现 KEY 长按检测 | 填 `convert_event_cb` 中 KEY_DOWN/KEY_UP 分支，用 `key_press_start_time` 计时 |
| 实现 KEY 短按检测 | KEY_DOWN → KEY_UP 间隔 < 阈值 → 触发 CLICKED |
| 扩展 `ipgui_widget_evt.h` | 添加 `LONG_PRESSED`、`CLICKED`、`DOUBLE_CLICKED` 事件类型 |
| 防止长按重复触发 | 用 `key_long_press_triggered` 标记 |

双击先不做——在没有键盘控件的阶段，双击没有使用场景。

### 第四阶段：最简布局系统

**目标：** 用户创建控件不需要手动算坐标。

简单实现——在 widget 加一个 `arrange_cb`，默认叠加排列（y 轴递增），可选水平排列。用户在创建时指定父容器，子控件自动排布。

### 第五阶段：文档

| 文档 | 内容 |
|---|---|
| `README.md` | 项目简介、特性列表、快速开始、API 概览 |
| `API.md` | 控件创建/销毁、事件处理、渲染定制 |
| `PORTING.md` | 如何移植到新平台（实现 display 和 input 回调） |

### 第六阶段：CI 和持续集成

| 任务 | 说明 |
|---|---|
| GitHub Actions | Ubuntu GCC 自动编译 |
| 代码格式检查 | clang-format 统一风格 |

## 四、不做的事情（明确边界）

1. **不追求 30 个控件。** 6 个核心控件够支撑 demo 和评估。差异化在渲染质量，不在控件数量。
2. **不降低渲染深度。** SDF 阴影、亚像素光栅化、距离场反走样是核心壁垒，不会为了轻量化自废武功。
3. **不做 GUI 设计器。** SGL 的 UI Designer 是产品级投入，现阶段不该做。
4. **不做多平台 CI。** 先只保 Ubuntu GCC，其他平台等有社区需求再加。
